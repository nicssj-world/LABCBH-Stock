# PR Checklist Attachment Grouping Design

## Goal

จัดกลุ่มช่องแนบเอกสารตามความหมายของเอกสาร แยก “ประเภทเอกสาร”, “ลำดับบริษัท” และ “สถานะการแนบ” ออกจากกัน เพื่อให้ผู้ใช้ตรวจความครบถ้วนก่อนส่งใบ PR ได้โดยไม่ตีความเลขในวงกลมผิด

## Problem

หน้าปัจจุบันแสดงเอกสารทั้ง 5 ไฟล์ใน grid เดียวและใช้ `requirement.slot` ในวงกลมหน้าชื่อทุกการ์ด ค่า `slot` เป็นลำดับภายในชนิดเอกสาร ไม่ใช่ลำดับ checklist ทั้งหมด จึงเกิดเลข `1` ซ้ำที่ TOR, ใบเสนอราคาบริษัทที่ 1 และแผนรายการซื้อ อีกทั้งชื่อใบเสนอราคาแสดง “บริษัทที่ 1” ซ้ำกับเลขในวงกลม ทำให้เลขเดียวกันดูเหมือนสื่อทั้งขั้นตอน ลำดับเอกสาร และลำดับบริษัท

## Information Architecture

ส่วน “เอกสารแนบ” แบ่งเป็นสองกลุ่มตามความหมาย:

1. **เอกสารหลัก** — TOR และแผนที่มีลำดับรายการที่ต้องการซื้อ แสดงเฉพาะรายการที่ policy ปัจจุบันกำหนดให้ต้องแนบ
2. **ใบเสนอราคาจากบริษัท** — รวมใบเสนอราคาทุก slot ไว้ใต้หัวข้อเดียว ชื่อการ์ดแสดง `บริษัทที่ 1`, `บริษัทที่ 2`, `บริษัทที่ 3` ตามจำนวนที่ policy ปัจจุบันกำหนด

หากวิธีจัดซื้อไม่ต้องใช้เอกสารชนิดใด กลุ่มหรือรายการนั้นจะไม่ถูกแสดง ไม่มี placeholder สำหรับเอกสารที่ policy ไม่ได้ร้องขอ

## Card and Status Design

- เอาวงกลมเลขออกจากการ์ดทุกชนิด
- การ์ดเอกสารหลักใช้ชื่อเอกสารเป็น label หลักโดยตรง
- หัวข้อกลุ่มใบเสนอราคาให้บริบทว่าเอกสารทุกใบเป็น “ใบเสนอราคา” จึงใช้ชื่อการ์ดสั้นว่า `บริษัทที่ N` โดย accessible name ของ file input ยังคงระบุเต็มว่า `แนบใบเสนอราคา บริษัทที่ N`
- มุมขวาของหัวการ์ดแสดงสถานะเป็นข้อความพร้อมสัญลักษณ์: `รอแนบ` เมื่อยังไม่มีไฟล์ และ `✓ แนบแล้ว` เมื่อไฟล์ผ่าน validation หรือมีไฟล์เดิมอยู่แล้ว
- สีช่วยเน้นสถานะ แต่ข้อความและสัญลักษณ์ต้องทำให้เข้าใจได้โดยไม่พึ่งสี
- เมื่อมีไฟล์ที่เลือกไม่ผ่าน validation ให้แสดง error ใกล้การ์ดเดิม และสถานะยังคงเป็น `รอแนบ`

## Progress Copy

หัวข้อรวมของส่วนเอกสารเปลี่ยนจากจำนวนที่ต้องแนบอย่างเดียวเป็น `แนบแล้ว X/Y ไฟล์` โดยนับเฉพาะไฟล์ที่ complete ตาม logic เดิม

แต่ละกลุ่มแสดง progress ของตนเอง:

- `แนบแล้ว X/Y` สำหรับเอกสารหลัก
- `แนบแล้ว X/Y` สำหรับใบเสนอราคา

ตัวนับทั้งหมดคำนวณจาก `policy.attachments` และสถานะไฟล์ที่มีอยู่จริง ไม่กำหนดจำนวน 2 หรือ 3 แบบ hardcode เพื่อให้รองรับวิธีจัดซื้อและ threshold เดิม

## Layout and Responsive Behavior

- Desktop ตั้งแต่ 1181px: เอกสารหลักใช้ grid สูงสุด 2 คอลัมน์ และใบเสนอราคาใช้ grid สูงสุด 3 คอลัมน์
- ช่วง 701–1180px: ทุกกลุ่มใช้ 2 คอลัมน์ โดยใบเสนอราคาลำดับถัดไปตัดขึ้นแถวใหม่ตาม DOM order
- ช่วงไม่เกิน 700px: ทุกกลุ่มใช้ 1 คอลัมน์
- ลำดับ DOM และ keyboard traversal คือเอกสารหลักก่อน แล้วตามด้วยใบเสนอราคาบริษัทที่ 1 ถึงบริษัทสุดท้าย
- ใช้ spacing, border, surface, radius และ focus state จาก design tokens เดิมของ Laboratory Control Bench; ไม่เพิ่ม styling system หรือ dependency ใหม่

## Data Flow and Validation

การเปลี่ยนแปลงเป็น presentation-only:

- ใช้ `derivePurchaseRequestChecklist(method, total)` เป็นแหล่งข้อมูลเดิม
- ใช้ `kind` เพื่อสร้างกลุ่ม และใช้ `slot` เฉพาะลำดับบริษัทกับ slot key
- คง `purchaseRequestAttachmentSlotKey`, `onFileChange`, drag-and-drop, click-to-select, existing attachment replacement, MIME validation, ขนาดสูงสุด 20 MB และ upload flow เดิมทั้งหมด
- ไม่เปลี่ยน policy, schema, API, storage หรือกฎการส่งใบ PR

## Accessibility and Copy

- โครงสร้างหัวข้อเรียงตามลำดับ: ส่วนเอกสาร → หัวข้อกลุ่ม → label ของการ์ด
- file input ทุกช่องมี visible label และ accessible name ที่ระบุชนิดเอกสารครบถ้วน
- สถานะไม่สื่อด้วยสีอย่างเดียว และตัวนับความครบถ้วนที่เปลี่ยนหลังเลือกไฟล์อยู่ใน `aria-live="polite"`
- focus ring, keyboard activation และ touch target อย่างน้อย 44px คงอยู่ตามข้อกำหนดเดิม
- ข้อความภาษาไทยใช้คำว่า `แนบแล้ว`, `รอแนบ`, `เอกสารหลัก` และ `ใบเสนอราคาจากบริษัท` อย่างสม่ำเสมอ

## Verification

- เพิ่ม UI contract tests ให้ยืนยันว่ามีสองกลุ่มและไม่มีการ render `requirement.slot` เป็นวงกลมสถานะอีก
- ทดสอบจำนวนใบเสนอราคา 1 และ 3 บริษัท รวมถึงกรณีมีหรือไม่มีแผนรายการซื้อ
- ทดสอบสถานะว่าง, เลือกไฟล์ใหม่, ไฟล์ไม่ผ่าน validation, มีไฟล์เดิม และเลือกไฟล์ใหม่เพื่อแทนที่
- รัน `npm run test:pr`, `npm run typecheck` และ `npm run lint`
- เปิดตรวจ desktop, tablet และ mobile โดยเฉพาะลำดับ 3/2/1 คอลัมน์, keyboard traversal, focus state และข้อความสถานะ
- หลังแก้ UI ให้รัน Impeccable detector หนึ่งครั้งกับไฟล์ที่เปลี่ยน และแก้ finding ที่เกิดจากงานนี้ในรอบเดียว

## Out of Scope

- การเพิ่มช่องชื่อบริษัทหรือการเปลี่ยน metadata ของใบเสนอราคา
- การเปลี่ยนจำนวนเอกสารที่ต้องแนบตามวิธีจัดซื้อหรือวงเงิน
- การเปลี่ยนส่วนรายชื่อคณะกรรมการ
- การเปลี่ยน upload, R2 storage, retention หรือ download behavior
